# Pull Request 规范

[English](../../en/development/pull-requests.md) | **中文**

所有改动都通过 Pull Request（PR）进入 `main`，维护者的改动也不例外。

## 提 PR 之前

- [ ] 分支基于最新的 `main`，并且符合[命名规则](branching.md#分支命名)
- [ ] 这个改动只做一件事，无关的修复放到单独的 PR
- [ ] 本地测试通过：`uv run pytest`
- [ ] 代码检查、格式和类型检查通过：`uv run ruff check .`、`uv run ruff format --check .`、`uv run mypy src`
- [ ] 新功能有测试，修复的 bug 有回归测试
- [ ] 如果行为、配置或 API 有变化，文档已同步更新
- [ ] 如果依赖有变化，`uv.lock` 已更新并提交
- [ ] 没有包含密钥、凭证、个人数据或大型生成文件

## 标题

PR 标题会成为 `main` 上的 commit 信息，所以必须遵守[提交规范](commit-convention.md)：

```
feat(storage): add S3 session store
fix(api): return 404 instead of 500 for unknown session
docs: add development guidelines
```

标题格式不对的 PR 会被 CI 拒绝。

## 描述

按 PR 模板填写。一份好的描述要回答：

- **改了什么**：简要说明
- **为什么改**：要解决的问题或动机，并关联 issue：`Closes #12`
- **怎么改的**：采用的方案，以及放弃的其他方案（如果不是显而易见的话）
- **怎么测试的**：运行过的命令、手动测试步骤，必要时附上截图或日志
- **风险**：破坏性变更、数据迁移、配置变化、对性能或安全的影响
- **代码来源**：如果复制或改编了其他代码，注明出处

按照"审查者没看过 issue"的前提来写。如果要解释很久，说明这个 PR 可能太大了。

## PR 大小

小 PR 审查得更快，也更仔细。

- 有效改动尽量控制在 **约 400 行以内**（生成文件和锁文件不算）
- 大的工作拆成一系列 PR，每个 PR 合并后 `main` 都能正常工作。例如
  先加接口，再加实现，最后接入
- 单纯的移动文件和重命名放在独立的 PR，不要和逻辑改动混在一起
- 没做完的功能可以放在默认关闭的配置开关后面先合并

## 草稿 PR

如果希望尽早获得方向上的反馈，或者想让 CI 先跑起来，但工作还没完成，可以开**草稿 PR（Draft）**。
完成后点 **Ready for review**。除非作者主动邀请，审查者一般不会细看草稿 PR。

## 审查过程中

- 通过推送新 commit 来处理反馈。审查进行中尽量不要 force push，
  否则审查者很难看出改了什么。需要的话在最后再 rebase
- 回复每一条评论：要么改代码，要么说明为什么不改。不要默默忽略评论
- 讨论由**发起评论的审查者**标记为已解决，除非审查者说可以由你来标记
- 一轮修改完成后，点 🔄 按钮重新请求审查
- 推送新 commit 会使之前的批准失效，这是有意的设置

## 合并

满足以下条件后可以合并：

- [ ] 至少 1 位非作者的批准
- [ ] 所有必需的 CI 检查通过
- [ ] 所有讨论都已解决
- [ ] 分支已和 `main` 同步

然后：

- 使用 **Squash and merge** 合并，这是唯一启用的合并方式
- 检查 GitHub 生成的最终 commit 信息：保留 PR 标题作为标题，整理正文，
  删掉 "fix typo"、"address review" 之类的内容，让它成为有用的总结
- 由谁合并：通常由有写权限的作者自己合并，否则由批准的协作者合并
- 合并后分支自动删除

## 长期无进展的 PR

- 作者 **30 天**没有动静的 PR 会收到提醒
- 提醒后 **14 天**仍无回应，PR 可能会被关闭，之后随时可以重新打开
- 对于已经接近完成但被放弃的 PR，维护者可以接手完成，并通过 `Co-authored-by:` 脚注保留原作者的署名

## 回滚

如果合并的 PR 导致 `main` 出问题，首要任务是让 `main` 恢复正常：

- 在已合并的 PR 页面点 **Revert** 按钮，它会创建一个回滚 PR，按正常流程审查
- 查清问题后，再提一个新的 PR 修复
