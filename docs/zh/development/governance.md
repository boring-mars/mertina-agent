# 项目治理

[English](../../en/development/governance.md) | **中文**

本文说明项目中谁可以做什么，以及如何做决策。
这套模式有意保持轻量，会随着项目发展逐步调整。

## 角色

| 角色 | 谁 | 权限 |
|---|---|---|
| **贡献者（Contributor）** | 任何人 | 开 issue、（从 fork）提 PR、评论、审查 |
| **协作者（Collaborator）** | 受邀加入仓库的人 | 以上全部，另外可以向主仓库推送分支、批准 PR、合并已批准的 PR、分流处理 issue |
| **维护者（Maintainer）** | 仓库所有者（目前是 @boring-mars） | 以上全部，另外可以修改仓库设置和分支保护、管理协作者、发布版本、做最终决策 |

仓库目前属于个人账号，因此只有所有者拥有管理员权限。
如果以后项目迁移到 GitHub Organization，维护者角色会扩展到更多人。

## 适用于所有人的规则

`main` 的分支保护对所有角色生效，包括维护者，任何人都不能绕过：

- 禁止直接 push、force push 和删除 `main`
- 所有改动都必须通过 PR
- 每个 PR 至少需要一位非作者的批准
- 只允许 squash 合并

## 如何做决策

- **日常改动**（bug 修复、小功能、文档）：在 PR 中决定，一个批准加上 CI 通过即可。
- **重要改动**（新功能、公共 API 变更、新增依赖、架构调整）：先开 issue 或 Discussion 讨论。
  开始大量工作之前，给大家至少几天时间回应。
- **值得记录的设计决策**（例如存储后端的选择、部署模式）：
  写一份架构决策记录（ADR），以 PR 的形式提交。ADR 放在 `docs/adr/` 目录，
  按顺序编号（`0001-use-postgres-for-sessions.md`），内容包括背景、考虑过的方案、最终决定及其影响。
  ADR 被接受后不再修改，如果决策变了，就写一份新的 ADR 来取代它。
- **出现分歧时**：先在讨论中尽量达成共识。如果无法达成，由维护者做最终决定，并写下理由。

## 如何成为协作者

没有固定名额。一般在满足以下条件后会被邀请：

- 有多个有分量的 PR 被合并
- 建设性地审查过别人的 PR
- 理解并遵守这些规范

任何协作者都可以向维护者推荐人选。长期不活跃（例如六个月）的协作者可能会被移除写权限，
随时欢迎回来。

## 与上游的关系

Mertina Agent 基于 Hermes Agent 改造。是否以及如何跟进上游的改动（例如同步上游版本、移植特定修复）
属于重要改动，按上面的流程决策。从上游引入的代码必须保留原有的版权和许可证声明。
