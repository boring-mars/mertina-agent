# 代码审查

[English](../../en/development/code-review.md) | **中文**

代码审查保证 `main` 的质量，也让团队成员都了解代码。
任何人都可以参与审查，但只有协作者的批准才计入合并条件。

## 审查目标

按重要性排序：

1. **正确性**：它是否做到了声称的事情，包括边界情况和失败情况？
2. **安全性**：是否会给用户、用户数据或凭证带来风险？
3. **设计**：是否符合整体架构？是不是能解决问题的最简单方案？
4. **可维护性**：下一个人能否看懂并安全地修改？
5. **一致性**：是否遵守这些规范，是否和周围的代码风格一致？

格式、import 顺序和 lint 问题交给工具处理，审查者不需要在这些上花时间。

## 谁来审查

- GitHub 会根据 `.github/CODEOWNERS` 自动请求审查（添加该文件后生效）
- 作者也可以主动指定审查者
- 作者不能批准自己的 PR
- 涉及安全敏感模块（认证、权限、租户隔离、密钥处理）的改动，
  要找熟悉该模块的人审查

## 响应时间

- 争取在 **2 个工作日**内给出第一次回应。可以是完整的审查，也可以只是一句"我周五看"
- 如果没空审查，请直接说明，方便作者找其他人
- 作者：如果一周都没有回应，可以在 PR 里提醒审查者

## 审查者检查清单

**正确性**
- [ ] 改动是否解决了 PR 或 issue 里描述的问题？
- [ ] 是否处理了边界情况：空输入、`None`、超时、重试、并发请求？
- [ ] 错误是否被显式处理，而不是被吞掉？错误信息是否有用？

**安全性**（参见[安全](security.md)）
- [ ] 代码、测试、日志和错误信息中没有密钥或凭证
- [ ] 用户输入经过校验，没有注入风险（SQL、shell、路径穿越、通过工具调用的提示注入）
- [ ] 做了认证和授权检查，一个租户无法访问另一个租户的数据
- [ ] 新增的依赖有人维护、许可证兼容、并且确实需要

**设计**
- [ ] 代码放的位置对吗？是否重复实现了已有的功能？
- [ ] 公共 API、配置项和存储格式的命名是否合适？这些以后很难改
- [ ] 是否是破坏性变更？如果是，是否做了标记并提供了迁移方式？

**测试和文档**
- [ ] 测试是否覆盖了新行为？去掉改动后测试会失败吗？
- [ ] 文档、配置示例是否更新？PR 标题是否适合写进变更日志？

**运维**（这是一个云服务）
- [ ] 日志是否足以在生产环境排查问题，同时不记录敏感数据？
- [ ] 外部调用是否设置了超时和资源限制？
- [ ] 数据库或存储的迁移是否向后兼容，能否安全回滚？

## 如何写审查意见

- 具体说明并给出理由：写"`items` 为空时这里会出错，因为……"，而不是"这不对"
- 不确定时就提问："这里上传超时了会怎样？"
- 给出具体的修改建议。GitHub 的 **suggestion** 代码块可以让作者一键采纳
- 针对代码，不针对人。说"这个函数"，而不是"你"
- 做得好的地方也要指出来
- 标注每条意见的重要程度，让作者知道哪些会阻塞合并：

| 前缀 | 含义 |
|---|---|
| *（无前缀）* | 合并前必须处理 |
| `nit:` | 细枝末节或风格问题，作者可以不改 |
| `suggestion:` | 值得考虑，但不强制 |
| `question:` | 请解释一下，可能需要修改，也可能不需要 |
| `follow-up:` | 意见合理，但更适合放到单独的 PR 或 issue 里做 |

## 审查结论

- **Approve（批准）**：CI 通过后就可以合并。批准的同时留一些 `nit:` 意见没有问题
- **Comment（评论）**：只给反馈，不做结论。只审查了部分内容时用这个
- **Request changes（要求修改）**：合并前必须处理。要清楚说明需要改什么，
  作者回复后要及时重新审查

如果 PR 的方向不对，要在逐行评论之前尽早、友善地指出，并建议回到 issue 里讨论。

## 给作者的建议

- 请求审查之前，先自己看一遍 diff，很多问题一眼就能发现
- 不要把审查意见当成针对个人。每个人的代码都要被审查
- 如果不同意，说明你的理由。如果仍然无法达成一致，请维护者来决定
  （参见[项目治理](governance.md#如何做决策)）
- 如果一个问题来回讨论超过两轮，就改成语音沟通或者单独开 issue 讨论
