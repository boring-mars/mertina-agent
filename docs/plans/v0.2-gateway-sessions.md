## 1. 目标与范围

v0.2 完成一个单进程、单用户、仅监听本机的常驻服务：用户通过 HTTP 创建会话、发起运行、
接收 SSE、停止运行；服务重启后仍能读取历史并继续对话。

| 功能 | 需要交付的内容 | 范围来源 |
|---|---|---|
| Gateway 生命周期 | 启动配置校验、初始化资源、监听 HTTP、有界优雅关闭及资源释放 | ROADMAP |
| 会话管理 | 稳定的会话 ID、标题与时间信息；同会话串行，不同会话独立运行 | ROADMAP |
| 会话与消息存储 | 保存完整、有序、可回放的消息，原子提交一轮结果 | ROADMAP；事务边界为本计划建议 |
| 会话恢复 | 按 ID 加载历史，传给现有 Agent；重启后可继续普通及含工具的对话 | ROADMAP |
| Sessions API | 创建、列表、详情、改名、删除、读取消息；分页和输入校验 | ROADMAP |
| Runs API | 发起、查询状态、停止；任务生命周期独立于 HTTP 连接 | ROADMAP；状态查询支持重连 |
| SSE 与重连 | 文本、工具、重试与终态事件；连接断开后可重新附着仍在运行的任务 | ROADMAP |
| 本地运行限制 | 仅绑定 loopback；P0 无认证；单进程运行 | ROADMAP / README |
| 数据库选择与初始化 | 启动时指定后端和连接配置，提供初始化入口，集中处理后端差异 | 本次用户提出的范围扩展，方案待讨论 |

当前已确定首批支持 SQLite、PostgreSQL、MySQL，ROADMAP、README 已同步范围。
具体驱动、初始化权限与迁移承诺仍按阶段确定，会话业务在本期第二阶段交付，跨库历史迁移仍不在范围内。

不纳入本次基础实现：Web UI（v0.3）、memory/skills（v0.4）、cron（v0.5）、认证与云部署、
消息排队、跨进程协调、运行中任务的崩溃恢复、全文搜索和多租户。
数据库可配置不等于立即支持云部署，也不等于允许多个 Gateway 同时写同一数据库。

## 2. 开发要求和迁移原则

- 遵循 copy-then-cut，保留 Hermes 可复用的模块职责和行为，并记录删减及必要的结构调整。
- 沿用 README 已选定的 **aiohttp**、`gateway/`、`state/`，不另起一套 Web 框架或存储目录。
- Agent 与 tools 不依赖 Gateway、数据库驱动或 SQLAlchemy；Gateway 负责装配。
- 配置在启动时统一读取和校验，沿用 `Settings`、`load_settings()`、`MERTINA_` 前缀及环境变量优先于 `.env`。
- 公共接口使用精确类型；英文代码、日志及 Google 风格 docstring；异常集中在 `exceptions.py`。
- 异步路径不阻塞事件循环；外部连接有超时；不跨模型调用持有数据库事务。
- 复制代码保留 MIT 署名、固定 SHA 和来源链接；新增依赖经评估后用 uv 管理并更新锁文件。
- 大改动先讨论；实现按可验收的小 PR 拆分，尽量控制约 400 行有效改动。全部经 PR squash 合并。
- 本计划不调整包版本或发布 tag。涉及开发规范本身的修改，必须同时更新中英文版本。

## 3. 当前代码能直接复用的边界

| 现有文件 | 已有能力 | v0.2 使用方式 |
|---|---|---|
| `agent/core.py` | 异步 `run_conversation()`、`interrupt()`、实例防重入、资源关闭 | 会话层创建/管理独立 Agent，传入恢复历史 |
| `agent/turn_result.py` | `ConversationResult.messages` 是包含本轮的完整历史 | 从结果持久化，不从 SSE 重建历史 |
| `agent/transports/types.py` | `ChatMessage`、tool call/result、refusal 的准确字段 | 存储编解码保持字段和值，不只存 role/content |
| `agent/events.py` | 类型化进度事件及同步 `EventCallback` | 转成带 run ID、事件序号的 SSE envelope |
| `agent/turn_context.py` | 克隆历史、追加 user、组装模型请求 | 继续复用；避免 Gateway 重复追加本轮输入 |
| `config.py`、`exceptions.py` | 启动配置与统一异常体系 | 扩展 Gateway/DB 配置及异常 |
| `tests/unit/agent/conftest.py` | fake 模型、历史可回放断言 | 复用测试思路；需要跨目录时提取为公共测试辅助 |

两个必须处理的集成细节：

1. `EventCallback` 是同步观察接口，回调异常只记录日志。数据库写入不能依靠这个回调确认成功。
2. Agent 在 `run_conversation()` 返回前已发送终态事件。Gateway 暂存该事件，等待返回结果、
   历史提交成功后才发布成功/停止终态。落库失败必须返回存储失败，不能让客户端误以为历史已保存。

## 4. 建议的行为契约

以下是实现前需要评审的建议，不是已经发布的 API。

### 会话、运行与事务

- `session_id` 标识长期会话；`run_id` 标识一次 HTTP 发起的运行；SSE `event_id` 在该 run 内递增。
- 会话详情提供 `active_run_id` 或等效查询，让刷新后的客户端能找到活动 run；这个字段来自
  当前进程的运行登记，不代表该 run 可在进程重启后续跑。
- 同一 session 有运行或正在提交结果时，新 run 返回 `409`；暂不排队。不同 session 可并发。
- 同会话锁在读取历史**之前**取得，覆盖执行、历史提交和终态登记，最后释放；异常路径同样释放。
- 删除运行中的 session 建议返回 `409`；完成后删除 sessions/messages 使用事务，清理关联内存缓存。
- 会话内消息用显式序号排序；业务 ID 由应用生成。JSON 保留缺失字段与 null 的区别以及工具参数原文。
- 第一版建议只持久化已经正常收尾的轮次（成功、协作停止或已收尾失败）。历史尾部与会话更新时间
  一次提交；同一提交重试须可识别，不重复写消息。确定的提交标识及版本检查写入存储契约。
  可采用消息上的 `run_id` / 轮内序号唯一约束及 session revision，具体字段在 ADR 定稿；
  提交幂等不能隐含要求增加一张持久化 runs 业务表。
- `ConversationResult.messages` 包含旧历史；必须基于锁内读取的长度/版本提取本轮增量，
  并验证既有前缀未变，不能把完整历史每次重复追加，也不能用 `final_response` 覆盖真实历史尾部。
- 前端已看到的 delta 是暂态输出。强制杀进程可能丢失尚未提交的当前轮；已提交历史必须保留。
  若要求逐消息、逐工具调用防崩溃保存，需另行设计 durable checkpoint，不能复用进度事件冒充。
- 正常停服先停止接受新 run，向活动 Agent 发协作中断，给收尾和落库有界时间，最后释放资源。
  超时强制取消属于未完成轮次，不报告为已持久化完成。
- Agent 对象、模型客户端和运行缓存需要明确所有权及回收上限，不能随会话数量无限增长。

### 恢复与 SSE

- 正常恢复：加载有序消息并通过现有 transport 契约校验，再传入 `conversation_history`。
  测试必须包含工具调用、工具结果、refusal、停止后的部分回答及失败收尾。
- 自动生成的 system prompt 目前不在结果历史内。默认恢复时按当前启动配置重建；
  如需跨重启保留自定义 system prompt 或逐字复现旧提示词，应先定义会话配置快照的持久化范围。
- HTTP 断开只取消订阅，不取消后台 run；停止由独立接口触发，并且要处理启动前的停止竞态。
- 固定 Hermes 基线的 `_handle_run_events()` 在断开清理时删除 run transport；
  [这一段](https://github.com/NousResearch/hermes-agent/blob/4cefeed7debc7091ed65240cbc7e2c36435c0b6b/gateway/platforms/api_server_runs.py#L888)
  需要有意改造，不能照抄后宣称具备重连能力。多订阅者使用广播，重放与实时接入必须原子衔接。
- 采用有界事件缓存、心跳及完成后的保留期限；慢订阅者不能阻塞 Agent，也不能无限占用内存。
- 支持按 `Last-Event-ID` 重放仍保留的事件再接实时流；游标过期明确返回“需重新同步”，
  不能静默跳过。活动 run 提供可重建显示的状态快照；终态以已存消息为准。
- `RetryScheduled` 表示当前模型尝试重启，前端需重置对应暂态文本，避免拼接两次尝试的回答。
- P0 的 run registry / SSE 缓存建议驻内存。服务重启后可恢复会话，但不承诺恢复旧 run ID、
  接续尚未结束的模型调用或重放全部旧 SSE；这些属于另一层持久化要求。

### HTTP 接口草案

| 方法 / 路径 | 行为 |
|---|---|
| `POST /api/sessions` | 创建空会话 |
| `GET /api/sessions` | 按稳定排序分页列出会话 |
| `GET /api/sessions/{session_id}` | 读取会话详情 |
| `PATCH /api/sessions/{session_id}` | 修改标题 |
| `DELETE /api/sessions/{session_id}` | 删除会话及其消息 |
| `GET /api/sessions/{session_id}/messages` | 分页读取消息；服务内部恢复加载完整历史 |
| `POST /v1/runs` | 接受 session ID 和输入，返回 run ID 后后台执行 |
| `GET /v1/runs/{run_id}` | 查询运行状态及重连所需快照 |
| `GET /v1/runs/{run_id}/events` | SSE 订阅 / 重连 |
| `POST /v1/runs/{run_id}/stop` | 请求协作停止；重复请求有明确幂等语义 |

上述路径和方法已核对固定 Hermes 基线；请求/响应字段和错误码
在 API 检查点逐一收敛。无对象返回 `404`；冲突 `409`；校验及存储失败
统一映射为安全错误，不能泄漏 DSN、SQL 参数、提示词或堆栈。仅允许 loopback 监听，
同时明确 Host/Origin 校验和同源策略，避免本机无认证 API 被其他站点随意调用。

## 6. 多数据库设计：供下一轮讨论

建议采用下面的依赖关系；这是一项待决定的技术提案：

```text
Gateway / Session service
          |
          v
SessionStore 领域协议（会话、消息、一次轮次提交）
          |
          v
SessionDB 共用 SQL 实现 + schema / serialization
          |
          v
SQLAlchemy Core + async engine -> 方言 / 驱动 -> 配置选定的数据库
```

### 为什么划分这几层

- 业务接口表达“加载会话”“原子提交轮次”，不暴露 `execute_sql()`、连接或 ORM Session。
- 关系型数据库共用查询结构，让 SQLAlchemy 处理 SQL 编译及参数绑定；真实存在的连接选项、
  SQLite PRAGMA、方言特性等差异收敛在 `state/` 内。不会为每种数据库复制整套会话业务。
- 固定上游的 HTTP handler 存在直接 SQL 和私有 `db._execute_write()` 调用，例如
  [会话修改路径](https://github.com/NousResearch/hermes-agent/blob/4cefeed7debc7091ed65240cbc7e2c36435c0b6b/gateway/platforms/api_server.py#L2918)。
  迁移时必须收敛进公开的存储领域操作，避免把 SQLite 语法继续带到 Gateway。
- 方言层不能消除事务隔离、DDL、锁、JSON/日期类型、大小写排序、upsert 等语义差异。
  schema 优先采用可移植类型和操作；每个声明支持的后端都必须通过相同契约测试。
- 非关系型数据库如以后确有需求，应实现同一领域协议并满足提交语义；它不是换一个 SQL 驱动。
- 优先评估 SQLAlchemy Core + 异步驱动；是否引入 ORM 或 Alembic，依两表模型和迁移需求决定。
  迁移自动生成只产出候选脚本，必须人工审查并在每个支持后端验证。

### 启动配置和初始化的边界

- 建议一个 Gateway 进程启动时选择一个数据库，不按请求/会话选择，运行中不热切换。
- 沿用 `MERTINA_DATABASE_URL` 表达后端和连接；敏感字段不进入日志或校验错误。
  CLI 若提供选择参数，应映射进同一配置体系；具体优先级需在实现前写入测试。
- 缺失驱动、连接失败或版本不兼容时启动失败，不能悄悄改用 SQLite。
- 零配置默认 SQLite 是候选方案：创建应用数据目录、库文件、首次 schema，重复启动不破坏数据。
- 对 PostgreSQL/MySQL 等，建议先要求用户提供可连接的数据库及账户；程序仅在明确配置的目标内
  初始化表和迁移元数据。安装服务器、建库、建用户、授权是单独的 provisioning 范围。
- schema 初始化、既有 schema 升级、跨库搬迁数据是三件事。修改连接配置不会自动迁移旧会话。
  首次初始化可幂等执行；既有库升级走版本化迁移，破坏性变更不能在启动时静默执行。
- 可选配置向导由 Mertina 提供，只负责选择、校验、配置生成和约定范围的初始化。
  不调用运行中的模型生成并执行任意 SQL，也不引入整个 Hermes CLI。

### 需要与用户确定的内容

1. **首批支持名单（已确定）**：SQLite、PostgreSQL、MySQL；MariaDB 和其他数据库不在第一期。
2. **持久化时点**：接受“收尾后提交完整轮次”，还是要求正在运行的输入/工具过程也能抗崩溃恢复？
3. **初始化体验**：环境变量/配置文件即可，还是需要交互向导？自动化服务启动必须支持非交互方式。
4. **初始化权限**：只建表和维护 schema，还是还要协助部署数据库、建库建用户？后者需要独立设计。
5. **兼容的含义**：仅 Mertina 多后端一致行为，还是需要导入已有 Hermes SQLite 数据、
   或在不同后端间搬迁已有会话？这些需求分别增加 importer / migration 工作。
6. **会话配置**：重启后使用当前模型和 prompt，还是恢复创建时的非敏感配置快照？

上述决定应在存储实现前落实进 ADR；路线图的多数据库扩展通过同一系列 PR 留下决策记录。

技术依据：[SQLAlchemy Engine / dialect](https://docs.sqlalchemy.org/en/20/core/engines.html)、
[异步 Core 接口](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html#synopsis-core)、
[Alembic 自动迁移的限制](https://alembic.sqlalchemy.org/en/latest/autogenerate.html)。
这些资料支持候选设计，不表示当前仓库已选用或安装这些依赖。

## 7. 实施顺序与验收

| 检查点 | 交付物 | 核心验收 |
|---|---|---|
| CP0：方案与来源 | 完成上述讨论、ADR、来源/删减表、API 和支持矩阵；同步路线图范围 | 每项需求有明确去向，不混入后续版本能力 |
| CP1：存储契约与首个实现 | 领域模型、消息编解码、两表 schema、SQLite、基础初始化 | CRUD、顺序、工具消息往返、事务回滚、提交重试不重复 |
| CP2：确认的其他后端 | 第二后端、配置选型、迁移与初始化入口 | 所有承诺后端通过同套契约，连接/权限/版本错误可诊断 |
| CP3：会话与运行服务 | Session manager、lease、Run registry、落库终态顺序 | 同会话互斥、跨会话并发、停止后继续、存储失败不假成功 |
| CP4：Gateway 与 Sessions API | Runner、生命周期、aiohttp 路由、配置校验 | 本机监听、CRUD/分页/错误路径、停服清理 |
| CP5：Runs API 与 SSE | 后台 run、事件流、重连、停止 | 断开不取消；同 run 重连；游标过期/慢订阅/停止竞态 |
| CP6：重启和交付 | HTTP 示例、文档、数据库测试矩阵 | 仅 HTTP 完整闭环；重启后恢复含工具历史并继续对话 |

CP1/CP2 的具体顺序可按 ADR 调整，不能先把 Gateway 绑死到 `sqlite3` 再补一个抽象空壳。
每个检查点可以再拆为多个小 PR；每次合入都保持 main 可构建、可测试。
