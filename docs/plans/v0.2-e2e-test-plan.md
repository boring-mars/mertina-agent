# v0.2 端到端测试与三库对比计划

日期：2026-11-10。状态：B 已完成，结果见 [v0.2-e2e 报告](../testing/v0.2-e2e/README.md)；A 等待可用的真实模型凭据。分支：`feat/gateway-sessions`。

## 1. 目标与两条测试线

| 测试线 | 模型 | 方式 | 回答的问题 |
|---|---|---|---|
| A. 功能验收 | 真实模型 | 用户按用例手动对话（CLI 或 HTTP），再进库查看 | 真实场景下流程和存储是否正确 |
| B. 三库对比 | 确定性假模型 | 脚本自动跑用例，按监测点采集数据 | SQLite、PostgreSQL、MySQL 在相同负载下的耗时、空间与内容一致性 |

B 不使用真实模型：真实模型每轮耗时以秒计且波动大，会淹没毫秒级的数据库差异；
回答也不确定，三库存储内容无法逐字比对。A 依赖 provider 解除 IP 白名单限制（目前返回 HTTP 403）。

用户确认的选择：

- 两条线都做，先完成 B 的工具和数据，再做 A。
- 不补 token 用量与模型调用次数的采集，产品代码不为本次测试改动。
- B 做基础用例加历史增长曲线，不做并发压测。
- 汇总报告提交到 `docs/testing/v0.2-e2e/`；原始数据放在 git 忽略的 `dev/e2e/results/`。

## 2. 监测点

服务端阶段（CP2–CP4）在测试专用的 Gateway 启动器 `dev/e2e/serve_gateway.py` 进程内计时：
它在启动时给 `SessionDB` 的方法和 Agent 套上计时包装，产品代码不变。只靠客户端的 SSE 到达时间不够准：
订阅在发起 run 之后才建立，早期事件会以回放方式一次性到达。客户端仍记录 HTTP 延迟、端到端耗时和读回结果。

| 监测点 | 区间或来源 | 记录 |
|---|---|---|
| CP1 请求受理 | `POST /v1/runs` 到收到 202 | 受理延迟 |
| CP2 加载历史 | `run.accepted` → `run.started` | 耗时；本轮开始前的历史条数与字节数 |
| CP3 模型阶段 | `run.started` → `run.committing` | 首个 `text.delta` 延迟、工具调用次数与 `tool.finished.duration_s`、`retry.scheduled` 次数 |
| CP4 落库 | `run.committing` → 终态事件 | 提交事务耗时；本轮写入的消息条数与字节数；`revision` |
| CP5 一致性 | 查库 | `message_count` 等于最大 `seq` 且 `seq` 连续；每轮有对应 `commits` 行且区间衔接；终态 `durable=true` |
| CP6 读回 | `GET /api/sessions/{id}/messages` | 读取延迟；读回内容与预期逐条相同 |
| 会话级 | Sessions API 与查库 | 创建、列表、改名、删除延迟；删除后级联清空；各库占用空间 |

CP2 包含创建 Agent 的时间，CP4 包含事件发布的时间；两者都在同一进程内，三库之间可比，
但不等于纯数据库操作耗时。

## 3. 对话用例

| # | 用例 | 重点检查 |
|---|---|---|
| 1 | 普通多轮对话（3 轮） | `seq` 连续、`history_revision` 每轮加 1、标题取自第一句 |
| 2 | 中文、emoji、超过 64 KiB 的长文本 | 读回无损；MySQL 表为 utf8mb4_bin、payload 为 LONGTEXT |
| 3 | 触发工具调用 | assistant `tool_calls` 与 tool 消息的顺序和 `tool_call_id` 对应 |
| 4 | 回答中途停止 | `commits.status=stopped`；部分回答已保存；未回答的工具调用已闭合 |
| 5 | 重启后续聊 | Gateway 重启或 CLI `--resume` 后历史连续，没有重复写入 |
| 6 | 两个会话并发；同一会话发第二个 run | 会话互不影响；同会话返回 409 且库中无多余数据 |
| 7 | 改名与删除 | 过期 `expected_version` 返回 409；`metadata_version` 递增；删除后 messages、commits 清空 |
| 8 | 跨入口 | CLI 写入的会话可通过 Gateway API 原样读出 |

B 中所有用例由脚本执行；用例 5 的 CLI 部分和用例 8 在 A 中手动完成。

## 4. 历史增长曲线（仅 B）

同一会话连续发送 200 轮，在第 1、10、50、100、200 轮记录 CP2、CP4 和 CP6（读取第一页）。
每个库跑同样的脚本，结果画成"历史条数-耗时"曲线并列出数值。

## 5. 工具（`dev/e2e/`，不进产品包）

- `stub_model.py`：确定性的 OpenAI 兼容端点；支持流式、工具调用、可被中断的慢回答和超过 64 KiB 的回答。
- `serve_gateway.py`：测试用 Gateway 启动器；用确定性的 `lookup` 工具代替会联网的 `web_search`，
  并把每轮的服务端计时写入 trace JSONL（只记大小与耗时，不记消息内容）。
- `run_cases.py`：通过 HTTP 跑用例与增长曲线，每个事件带时间戳写入 JSONL，结束后输出 CSV 汇总。
- `inspect_db.py`（避免与标准库 `inspect` 重名）：三库共用的查库工具，打印会话、解码后的消息与提交凭据，自动检查 CP5，
  并为每条消息计算哈希，比较三库存储内容是否完全一致。
- `queries/`：三种库各一份手写查询 SQL，供手动进库查看。
- `report.py`：汇总三库结果，生成 `docs/testing/v0.2-e2e/README.md` 的对比表与曲线数据。

每个库的执行流程：设置 `MERTINA_DATABASE_URL` → `mertina db init` → 启动假模型与 Gateway →
`run_cases.py` → `inspect_db.py` → 停止服务。三库完成后运行 `report.py`。
每次运行使用干净的数据：SQLite 用新文件；PostgreSQL、MySQL 先删除 `mertina_` 前缀的四张表再初始化
（Gateway 的表前缀固定，不能按运行区分）。只操作 `mertina_dev` 开发库，不碰其他项目的数据。

## 6. 局限

- SQLite 在进程内读写本地文件；PostgreSQL、MySQL 运行在 macOS 的 Docker 虚拟机中，
  每次访问都经过虚拟网络。对比结果反映的是本机开发环境，不代表生产部署的性能。
- 计时在客户端完成，包含本机 HTTP 与事件循环调度的开销。
- 假模型不能验证真实模型的流式行为和回答质量，这部分由 A 覆盖。
