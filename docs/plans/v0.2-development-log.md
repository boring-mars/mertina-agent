## 开发者 CLI

2026-11-10，按用户要求在 `feat/cli` 分支上新增一个方便开发的 `mertina` 命令（`src/mertina_agent/cli.py`），
不是 P2 规划中的本地客户端：

- 不带参数的 `mertina`（或 `chat`、`run`）在 CLI 进程内直接运行 Agent，逐轮落库，可以 `--resume` 续聊；
  另有 `sessions`、`db init|check`、`gateway` 子命令，后两个包装原有的 `python -m` 入口。
- 配置文件查找顺序：`--env-file` > `./.env` > `~/.mertina/.env`；环境变量始终优先。
- 第一次 Ctrl+C 协作停止并保存已生成的内容，第二次放弃本轮且不保存。
- 把判断一轮以何种状态结束的逻辑抽成 `state.serialization.turn_status()`，CLI 与 Gateway 共用。

实现中发现并修复了 Gateway 的一个问题：提交时如果存储因历史版本变化而明确拒绝（`SessionConflictError`，
另一进程改写或删除了会话），原代码把它当成结果未知，标记需要核对且不释放会话锁，
导致该会话在 Gateway 中一直返回 409，并持续占用活动名额。现在按明确失败处理（`history_conflict`），
释放锁，并补了回归测试。单进程内由会话锁保证不会出现这种冲突，CLI 与 Gateway 同时写同一会话时才会触发。

验证：CLI 单元测试与 SQLite 集成测试（含真实 SIGINT 停止和放弃轮次）；在仓库外的目录用本地假模型
手动跑通了未初始化提示、`db init`、两轮对话、`/sessions`、`run --resume` 续聊和不存在会话的报错。

## 端到端测试与三库对比（B 线）

2026-11-10，按 [端到端测试计划](v0.2-e2e-test-plan.md) 在 `dev/e2e/` 实现测试工具，并在三种后端上完成一次完整运行，
报告见 [docs/testing/v0.2-e2e](../testing/v0.2-e2e/README.md)。结果：

- 三种后端 8 个用例全部通过（每库 82 项检查），库内一致性检查无问题；三库存储内容逐条一致（9 个会话、426 条消息）。
- 落库耗时不随历史增长：每轮只写本轮新增的消息，200 轮内 SQLite 约 1.5 ms，PostgreSQL、MySQL 约 3–5 ms。
- 加载历史随历史长度线性增长：每轮都读取完整历史，398 条消息时约 3.4 ms（SQLite）、4.4 ms（MySQL）、
  6.8 ms（PostgreSQL）。相对真实模型的秒级耗时可以忽略；超长会话由 P1 的上下文压缩限制。
- 单条 100 KiB 回答的落库，MySQL（LONGTEXT）约 35 ms，明显高于 PostgreSQL（约 8 ms）和 SQLite（约 3 ms）。
- 空间占用与 payload 之比：PostgreSQL 1.28（TOAST 压缩大字段），SQLite 1.39，MySQL 1.64（16 KiB 页）。
- PostgreSQL、MySQL 在 Docker 虚拟机中运行，差异包含虚拟网络开销，不代表生产环境。

## 真实模型功能验收（A 线）

2026-11-11，用户更换有效的 DeepSeek key 后（模型 `deepseek-flash`），在单独的 SQLite 文件上用 CLI 和 Gateway
做真实对话，再用 `dev/e2e/inspect_db.py` 查库。原始日志在 git 忽略的 `dev/e2e/results/real-20261111/`。

| 用例 | 入口 | 结果 |
|---|---|---|
| 多轮对话与上下文 | CLI | 第一轮告诉模型代号，第二轮能答出；`/sessions` 列出会话 |
| 工具调用（DuckDuckGo） | CLI | 模型 3 轮共发起 5 次 `web_search`，前 3 次失败（mojeek TLS 握手错误、"No results found"），模型换短查询后成功，回答附来源 |
| 重启后续聊 | CLI `--resume` | 新进程读回 14 条历史，模型能复述之前的对话和搜索结果 |
| 跨入口 | Gateway | 继续 CLI 写入的会话，revision 从 4 接到 5；`GET /messages` 读回 CLI 写入的全部消息 |
| 工具调用（并行） | Gateway | 3 次 `web_search`（其中 2 次并行），事件顺序正确，`durable=true` |
| 中途停止 | Gateway `--stop-after 4` | `run.stopped`，已流式输出的 433 个字符完整落库，commits 记为 `stopped` |
| Gateway 重启后续聊 | Gateway | 重启后继续被停止的会话，模型准确说出文章停在哪一句 |

查库：3 个会话、29 条消息、8 条提交凭据，一致性检查全部通过；失败的搜索也作为 tool 消息完整保存，
`tool_call_id` 与 assistant 的 `tool_calls` 一一对应。

发现与处理：

- 不带子命令的 `mertina --resume ID` 被 argparse 拒绝，只有 `mertina chat --resume ID` 可用。
  已让 `--resume` 也能写在子命令之前（与 `--env-file` 一样用 `SUPPRESS` 默认值，避免被子命令覆盖），
  用于 `sessions` 等不对话的命令时报错；补了单元测试并用真实模型验证。
- DuckDuckGo 后端（ddgs）不稳定：单次 6–18 秒，约一半请求失败，失败时 provider 以 WARNING 打到 stderr，
  在 CLI 里会和回答混在一起显示。目前不影响正确性，暂不处理，记为后续改进。
- Gateway 收到 SIGINT 后正常退出（退出码 0）。测试中一次退出码 1 是 `pkill -f` 同时命中了外层 shell，不是 Gateway 的问题。
