# v0.1 第二阶段开发计划书：模型接入层

编制日期：2026-09-20。状态：代码实现、离线验收和指定真实端点验收均已完成。
实际开发、复查修正和验证结果见[开发与验收记录](v0.1-phase-2-development-log.md)。

## 1. 阶段定位与交付目标

这是 **v0.1 内部的第二个实施阶段**，接续已经完成验收的工程骨架与配置基线。
它不对应路线图中的 v0.2；v0.2 的 Gateway、HTTP API 和会话存储仍按原路线图推进。

本阶段交付一个可被后续 Agent 循环复用的 Python 模型接入层：

> 使用已有配置，向标准 OpenAI-compatible Chat Completions 端点发出一次非流式请求，
> 将返回的文本、工具调用、结束原因和用量整理成统一结果，并让失败行为可测试、可辨识。

用户可观察到的成果是一个可显式运行的示例脚本。它能得到模型回答，也能展示模型要求调用的工具，
但不会执行工具。自动化测试全部离线；真实模型调用作为独立的手动验收。

依据：[项目路线图](../../ROADMAP.md)、[编码规范](../zh/development/coding-style.md)、
[测试规范](../zh/development/testing.md)、[PR 规范](../zh/development/pull-requests.md)。

## 4. 架构与接口设计

```text
调用方 / 手动示例 / 后续 Agent
             │ 完整消息列表 + 可选工具定义
             ▼
        ModelClient                 负责配置、请求、异常和资源
             │
       ProviderTransport            负责请求与响应格式
             │
  ChatCompletionsTransport
             │
      异步 OpenAI SDK ────── 标准兼容端点
             │
             ▼
      NormalizedResponse
```

Transport 不访问网络、不读取环境变量、不维护会话、不执行工具。
ModelClient 不循环调用模型、不更新消息历史，不根据结束原因自动发起第二次请求。

### 4.1 数据契约

| 类型 | 字段与规则 |
|---|---|
| `ChatMessage` | 使用区分 role 的类型化联合；支持 `system`、`developer`、`user`、`assistant`、`tool`；文本为字符串，assistant 工具请求允许正文为 `None` |
| `ToolDefinition` | 仅 function 工具；函数名称、描述和参数 JSON Schema；JSON 值使用明确的递归类型，不以公共 `dict[str, Any]` 代替 |
| `ToolCall` | 非空 `id`、非空 `name`、字符串 `arguments`；参数保留原文，不在此解析、修补或执行 |
| `Usage` | `prompt_tokens`、`completion_tokens`、`total_tokens`，每个为非负整数或 `None`；不从缺失字段推导假值 |
| `NormalizedResponse` | `content: str | None`、有序 `tool_calls`、`finish_reason: str`、`refusal: str | None`、`usage: Usage | None` |

保留 Hermes 的类型名称和核心概念。`ToolCall`、`Usage`、`NormalizedResponse` 建议采用 frozen dataclass，
工具调用使用不可变序列。传入的消息/JSON Schema 如采用 TypedDict，必须另外在边界做运行时校验；
类型标注不能代替运行时检查。SDK 不透明对象仅允许在适配边界做必要转换。

### 4.2 公共调用契约

拟定入口：`ModelClient(settings, *, transport=None, sdk_client=None)`。

- `await complete(messages, *, tools=()) -> NormalizedResponse`：发送一次请求。
- `await aclose()`：关闭包装器；重复调用安全。
- 支持 `async with ModelClient(...) as client`，异常退出同样释放自有资源。
- `sdk_client` 注入路径同样受 Settings 和单次尝试策略约束，不能携带另一套生效配置；详见 4.5。
- 调用方传入完整历史；客户端不保存上一轮消息。
- `ProviderTransport` 保留 `convert_messages`、`convert_tools`、`build_kwargs`、`normalize_response`；
  结构检查可通过独立方法实现，但非法结构必须转为规定的响应异常。

输入契约同时覆盖历史回放中的 `tool_call_id`，避免后续 Agent 再替换消息表示。
本阶段不实现全会话状态机，也不自动为缺失的工具 ID 生成替代 ID。

### 4.3 请求序列化

- 发送配置指定的 `model` 和转换后的 `messages`，明确使用非流式模式。
- 单 choice 使用协议默认值；不开放批量候选选项，响应出现多个 choice 视为不符合本阶段契约。
- 工具为空时省略 `tools`；assistant 没有工具调用时省略空的 `tool_calls`。
- tool 结果保留 `tool_call_id` 与内容，不发送多余的 `name` 或项目内部字段。
- 只输出支持的协议字段；未知字段或不支持的多模态输入在调用前明确报错，不能静默丢掉用户内容。
- 不根据模型名称自动把 system 改为 developer；调用者选择受目标端点支持的 role。
- 不主动附加 temperature、推理配置、token 上限、缓存参数、厂商 `extra_body`。
- 序列化不能原地修改消息、工具列表或嵌套参数 Schema。

### 4.4 响应规则

- 非流式响应必须包含且仅包含一个 choice，包含合法 message 和非空字符串结束原因。
- 纯文本回答有效；没有文本但存在工具调用的响应也有效。
- 所有工具调用都保留顺序、ID、名称及参数；任一调用缺少必需字段，则整个响应报协议错误，不能静默丢失调用。
- `arguments` 不是合法 JSON 时仍保留原文；后续执行层负责判断能否执行。
- `stop`、`tool_calls`、`length`、`content_filter` 分别保留；未知的非空字符串结束原因原样保留，不能冒充 `stop`。
- 拒绝信息通过 `refusal` 单独表达；不将它混入推理内容，也不因拒绝自动重试。
- 正文为空、无工具、无拒绝且没有 `length` / `content_filter` 终止信息的响应报协议错误。
- `length` / `content_filter` 即使没有正文也返回可辨识结果；有截断迹象的工具参数不能被标成可安全执行。
- 没有 usage 时返回 `None`；真实全零用量保留为零；缺失部分计数保持 `None`，非法类型或负数报响应错误。

### 4.5 凭据、超时、重试与关闭

- 凭据仅来自传入的 Settings，不允许 SDK 自动读取另一套 `OPENAI_API_KEY`。
- `llm_api_key=None` 或空字符串视为无鉴权模式。若 SDK 构造器要求 key，可在内部使用固定非敏感占位值，
  但必须通过 SDK 支持的请求头覆盖方式移除 Authorization，并以模拟 HTTP 请求验证；不得发送全局真实密钥。
- `llm_base_url` 必须是带主机的 HTTP(S) base URL，不含内嵌凭据、query、fragment 或控制字符；
  不拆分或修复地址，避免 SDK 把资源路径拼进 query。模型名称非空，保留现有配置名和优先级。
- `llm_timeout_s` 作为 SDK 的网络操作超时；它不是整轮 Agent 或所有重试的总时间预算。
- 显式关闭 SDK 自动重试，本阶段每次 `complete()` 只尝试一次。429、5xx 等错误留给调用方。
  后续指数退避由一个上层模块统一负责，避免双层重试。
- 同时关闭 HTTP 自动重定向，307 等状态直接作为 HTTP 错误返回，不隐式发起第二次请求。
- 注入的 SDK 也必须通过所选 SDK 支持的 options 机制覆盖地址、凭据/无鉴权请求头、超时和重试配置，
  不原地修改外部实例。若无法可靠覆盖，构造时以 `ConfigurationError` 拒绝，不能带着冲突配置发请求。
  派生视图若共享外部连接资源，包装器不能关闭该共享资源；W1 必须验证这一路径。
- 注入 SDK 的底层 HTTP auth、额外 headers/query/cookies 或自动重定向若无法通过 SDK options
  安全覆盖，则在构造时拒绝，不修改外部对象。此只读兼容性检查局限于已测试的 SDK 边界。
- 客户端自行创建 SDK 实例时负责关闭；注入的 SDK 实例由调用方持有，不因包装器退出而被关闭。
- 包装器关闭后再次请求明确失败。`asyncio.CancelledError` 自然传播，不转换成普通请求错误。
  这不等于实现了产品级 stop 标志或中止后的历史修复。

### 4.6 异常与日志

在现有异常模块补充以下基于 `MertinaError` 的异常：

| 异常 | 使用场景 |
|---|---|
| `ModelInputError` | 非法 role、非文本输入、错误的工具定义或消息必需字段缺失 |
| `ModelRequestError` | 网络超时、连接失败、HTTP 错误、客户端已关闭；以 kind 区分，HTTP 场景保留 status_code |
| `ModelResponseError` | 响应结构损坏、缺失工具调用字段、无效用量等 |

配置错误继续使用 `ConfigurationError`。HTTP 错误可保留 `Retry-After` 作为后续重试的参考，
不能把整个响应 body 直接放进用户可见错误。已知 SDK 错误进行具体映射，保留异常链；
显示与日志使用经过控制的信息，不打印原始 SDK 异常、密钥、完整消息或请求体。
未知程序错误不应被笼统包装成“模型不可用”。

| T03 | 嵌套消息和工具 Schema | 调用前后输入完全相同，无原地修改 |
| T04 | 不支持的 role、多模态、非法必需字段 | 本地 ModelInputError，未发请求 |
| T05 | 普通文本响应 | 返回正文和实际 finish_reason |
| T06 | 纯工具响应、单个与多个调用 | content=None 合法，ID/顺序/名称/arguments 原文保留 |
| T07 | 工具参数为畸形 JSON | 原文保留，不尝试修补或执行 |
| T08 | usage 缺失、部分缺失、真实零值 | None 与真实 0 区分；不伪造统计 |
| T09 | refusal 与 length/content_filter | 可辨识拒绝/终止原因，允许相应空正文，不自动重试 |
| T10 | 空 choices、多 choice、无效 message、缺失结束原因 | ModelResponseError，不能悄悄返回成功 |
| T11 | 缺失工具 ID/name/arguments，非法用量 | ModelResponseError，不丢弃坏调用后继续 |
| T12 | 未知非空 finish_reason，带正常正文 | 原样保留，不降级为 stop |
| T13 | 显式配置，以及预配了不同端点/key/超时的注入 SDK | 模拟请求与 Settings 一致；无隐式配置回退，不能覆盖时构造即失败 |
| T14 | 无 key/空 key，且环境中存在诱饵 OPENAI_API_KEY | 请求不带 Authorization，也不使用诱饵值 |
| T15 | 超时、连接失败、401、429、5xx，以及预配自动重试的注入 SDK | kind/status_code 可辨识；仍只尝试一次；有 Retry-After 时可读取 |
| T16 | 正常及异常退出、重复关闭、关闭后调用 | 自有实例被关闭，外部实例不被关闭；后续调用明确失败 |
| T17 | 请求任务被取消 | CancelledError 传播；退出上下文时清理自有资源 |
| T18 | 失败日志和对外错误 | 不出现 key、诱饵凭据、完整消息或原始错误 body |
| T19 | 已有配置测试和全量检查 | 无既有行为回归，Ruff/mypy/pytest/pre-commit 通过 |
| T20 | 人工运行真实端点示例 | 能取得实际回答；记录模型、结果类别和检查结论，不记录秘密 |

实施阶段执行的质量检查：

```bash
uv run ruff check .
uv run ruff format --check .
uv run mypy src
uv run pytest
uv run pre-commit run --all-files
```

pre-commit 可能修复格式，执行后须检查 diff。不得为通过检查降低既有规则或删除失败断言。
现有 `integration` marker 不会自动排除测试；真实模型调用放在显式示例中，不能仅靠 marker 阻止联网。

## 8. 分层完成标准

### 8.1 代码与离线验收完成

- W1–W5 中的代码、离线测试、示例和文档完成，T01–T19 通过。
- 所有新代码符合项目类型与编码规范，无新增隐式 Hermes 运行时依赖。
- 依赖、来源、删减理由、许可证及配置说明齐全。
- 交付说明准确写明尚未支持的流式、重试、工具执行和中止能力。

### 8.2 真实模型验收完成

- 在用户提供或明确指定的端点及其所需凭据下，显式运行 T20 并记录结果；指定的无鉴权端点也可完成此验收。
- 默认 pytest、pre-commit 和 CI 不自动触发这一调用。
- 没有可用的指定端点，或该端点要求凭据但未提供时，状态为“离线验收完成，真实模型验收未执行”；
  不能把 mock 结果写成真实调用成功，也不能因无鉴权端点没有 key 就判定无法验收。

只有两层都满足，才能标记“第二阶段全部验收完成”。这仍不等于 v0.1 整体完成。

## 9. 风险、处理办法与后续衔接

| 风险或取舍 | 处理办法 |
|---|---|
| 上游变化造成来源不一致 | 统一固定 SHA，实施前核对；更换来源必须同步来源清单与测试 |
| 删除厂商兼容后部分模型不可用 | 公布标准协议子集；不承诺完整覆盖 Hermes 的所有 provider |
| SDK 默认重试/默认环境凭据改变行为 | W1 与 T14/T15 必测，明确单次尝试和显式鉴权 |
| 上游宽松数据依赖后续 Agent 修复 | 本阶段缺失关键 ID/结构明确报错；不照搬隐含的修复前提 |
| 未知用量或截断被当作成功完整结果 | 类型和 finish_reason 规则独立验证；不丢掉不确定状态 |
| 异步客户端资源归属不清 | 明确 owned/injected 两种情况及异常/取消测试 |
| 大文件搬迁引入不必要依赖 | 按符号提取，只迁已用逻辑；检查 import 图和 dependency diff |
| 无指定端点或缺少该端点所需凭据 | 完成所有离线工作，单独列出未执行的 T20；不擅自选用付费服务 |

后续流式工作可从 Hermes 的 `_ToolCallAccumulator` 提取工具参数分片合并算法，
但不能整份复制 `_StreamingCall` 的线程、relay、watchdog 和会话依赖。
后续 Agent 循环复用本阶段的结果类型与异常，负责工具执行、迭代预算、重试和 stop 历史修复。
